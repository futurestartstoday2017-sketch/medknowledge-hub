# MedKnowledge Hub 設計書

開発指示書 Ver.1.1〜1.3 と、その後の確認事項をまとめた設計書です。
実装はこの設計に沿って Step ごとに進めます。

## 1. 目的と前提

- メディカルアフェアーズ（MA）に必要な、製品・疾患・臨床研究・論文・規制・ライセンス・公開メディカル活動の知識を体系的に学ぶための**個人用**アプリ。
- 対象企業：杏林製薬株式会社（動作確認中は架空の企業名を使い、実製品の登録時に杏林製薬を対象企業として登録する）。
- 一般に公開されている情報のみを扱う。**実際の診療判断には使用しない。**
- ローカルPCのみで動作し、外部公開機能・クラウド・有料APIは使わない。

## 2. 設計の基本ルール

### ルール① 事実のテーブルには【出典セット】を付ける

医学的・規制的な事実を入れるテーブル（下の表で ◆ 印）には、すべて次の列を付ける。

| 列 | 内容 | DBでの制約 |
|---|---|---|
| source_version_id | 出典文書の版 | 必須 |
| source_location | 原文の該当箇所 | 必須（空文字不可） |
| status | 未確認 / 原文確認済み / 再確認要 | この3つのみ |
| verified_by, verified_at | 確認者・確認日時 | 「原文確認済み」には必須 |
| entry_method | 手入力 / CSV / API / AI抽出 | API・AI抽出は「未確認」でしか登録できない |
| is_current, superseded_by | 今の情報か / どの行に置き換えられたか | 削除禁止・内容の書き換え禁止（旧版を保持） |

### ルール② 「非公開」「未確認」を空欄と区別する

契約期間・特許満了日などには `disclosure`（公開 / 非公開 / 未確認）列を付け、「公開」のときだけ日付を必須にする。

### ルール③ 種類の違う日付は別テーブル・別の列名に分ける

承認日（approvals）、再審査期間（reexaminations）、特許満了日（patents）、契約期間（licenses）は混同しないよう別テーブルにする。
文書は **原文の改訂年月（revised_on）**・**入手日（retrieved_on）**・**確認日（confirmed_on）** を別々に記録する。

### ルール④ 事実と考察を分ける

エビデンスギャップ・考察・学習メモは `notes` テーブルに入れ、出典セットを持つ事実のテーブルと混ぜない。

### ルール⑤ 検出と確認を分け、更新はトランザクションで行う

1. 変更候補を `change_candidates` に登録する（検出）
2. 原文を確認し、新しい版を登録する
3. 古い行に「過去の情報」の印を付け、新しい行を追加し、`change_log` に変更前後・確認者・日時・理由を記録する（**1つのトランザクション**）
4. 変更候補を「反映済み」にする（確認）

`change_log`（更新履歴）は追記のみ。編集・削除はDBのトリガーで禁止する。

### ルール⑥ 外部から取得した情報は確認待ちにする

API・AIで取得・抽出した情報は「未確認」で保存し、人が原文を確認するまで確定情報にしない。
外部サイトへの自動アクセスは、利用規約・アクセス制限・技術仕様を確認するまで実装しない。

## 3. テーブル一覧

### A 基本（Step 3）

| テーブル | 内容 | 主な制約 |
|---|---|---|
| companies | 企業（name_ja, name_en, is_target） | 企業名の重複不可、対象企業は1社のみ |
| products | 製品（販売名, 一般名, 区分=対象企業/競合, 公式URL, 最終確認日） | 販売名の重複不可 |
| product_companies ◆ | 製造販売元・販売元（別々の行で管理） | 同じ組み合わせの重複不可 |
| diseases | 疾患（日本語名, 英語名） | 日本語名の重複不可 |
| indications | 適応症（製品×疾患） | 組み合わせの重複不可 |

### B 出典（Step 3）

| テーブル | 内容 | 主な制約 |
|---|---|---|
| documents | 文書（種別, タイトル, 発行元, 識別番号） | 種別＋識別番号の重複不可 |
| document_versions | 文書の版（版表記, 改訂年月, 入手日, 確認日, 原文URL, 最新版フラグ, 確認状態） | 版表記の重複不可、最新版は1つ、改訂年月の逆転不可 |
| document_links | 文書と製品・疾患の対応 | 製品か疾患のどちらか一方 |

### C 医学的情報・規制・ライセンス

| テーブル | Step | 内容 |
|---|---|---|
| medical_facts ◆ | 3 | 効能・効果、用法・用量、薬効分類、作用機序、投与経路、剤形、疾患概要、診断、治療、標準治療、アンメットニーズ など（対象は製品/疾患/適応症のどれか1つ） |
| safety_info ◆ | 3 | 安全性情報（警告、禁忌、重要な基本的注意、副作用 など）※独立テーブル |
| approvals ◆ | 9 | 承認（初回承認 / 効能・効果追加 / 用法・用量変更 / その他、承認年月日） |
| reexaminations ◆ | 9 | 再審査期間・終了日（disclosure 付き） |
| patents ◆ | 9 | 特許番号、種類、満了日、延長後の満了日（disclosure 付き） |
| licenses ◆ | 9 | 導入元・提携先、契約の種類、地域、契約期間、開示年度（disclosure 付き） |
| pms_studies ◆ | 9 | PMS（製造販売後調査等）：調査の種類、全例調査か、承認条件か、実施状況、目標症例数、実施期間（disclosure 付き）、登録番号 |

承認・再審査・特許・ライセンス・PMS は設計図バージョン2（`db/migrations/002_regulatory_pms.sql`）で追加。

- disclosure（公開状況）は 公開 / 非公開 / 未確認。「公開」のときだけ日付を入力でき、推測で日付を埋めない。
  画面では確認状態の「⚠️ 未確認（原文と未照合）」と区別して「❔ 未確認（公開情報で確認できていない）」と表示する。
- PMS の公開情報は、主に RMP（PMDA で公開）、添付文書の承認条件、審査報告書。製造販売後臨床試験は jRCT に登録されている場合がある（Step 10〜11 で確認する）。

**タイムライン（Step 9-2）**：初回承認年月日 → 再審査期間終了日 → 特許満了日（延長後があればその日）を並べ、
期間（約○年）と今日時点の経過・残りを表示する。計算に使うのは登録済みで「公開」の日付だけ。
未確認の値を含む場合はその旨を表示し、「後発品の参入時期を予測するものではない」と明記する。
エビデンス創出の計画を考えるための目安として使う。

### マイグレーション（設計図の変更）

- `db/schema.sql` = バージョン1（変更しない）。以降の変更は `db/migrations/` に番号付きのSQLとして追加し、
  `db/database.py` の `SCHEMA_VERSION` と `MIGRATIONS` に登録する。
- 新しいDBも既存のDBも、同じ手順（バージョン1から順に）で作られる。既存のDBを変更する前に自動でバックアップを取る。

### D 臨床試験（Step 10〜11）

| テーブル | 内容 |
|---|---|
| trials ◆ | 研究（タイトル, デザイン, フェーズ, スポンサー, 主要評価項目, 開始・終了日, 募集状況, 結果公開状況, 最終確認日） |
| trial_registrations ◆ | 登録番号（jRCT / UMIN-CTR / ClinicalTrials.gov）。レジストリ＋番号は重複不可。同じ試験の複数登録は1つの trial にまとめ、重複計上しない |
| trial_diseases / trial_interventions / trial_publications | 試験と疾患・試験薬・論文の対応 |

### E 論文（Step 12〜13）

| テーブル | 内容 |
|---|---|
| publications ◆ | PMID, DOI, タイトル, 掲載誌, 出版年, 抄録（ローカルDBに保存） |
| publication_authors | 著者ごとの所属原文と、対象企業所属の確認（確認済み・該当 / 確認済み・非該当 / 確認待ち） |
| publication_attributes ◆ | 社員著者あり / 企業資金提供 / 企業主導研究 を別々の属性として管理（該当 / 非該当 / 記載なし / 未確認） |
| publication_links | 論文と製品・疾患の対応 |

PubMed の所属検索：

- 対象：杏林製薬（Kyorin Pharmaceutical）と杏林製薬ホールディングス（Kyorin Holdings）
- **除外：杏林大学（Kyorin University）**
- 正確な英語表記と検索式は Step 13 で実際の所属表記を確認して決める
- NCBI へ送る連絡先メールアドレスは、Step 13 で利用規約を確認してから決める

### F メディカル活動（Step 14）

| テーブル | 内容 |
|---|---|
| medical_activities ◆ | 研究者主導研究支援 / 医学教育 / 疾患啓発 / 学会発表 / 論文公表 / 共同研究 / エビデンス創出、公開日、担当部門と確認状況 |
| activity_links | 活動と製品・疾患の対応 |

### G 学習・管理（Step 3）

| テーブル | 内容 |
|---|---|
| notes | 学習メモ / エビデンスギャップ / 考察 / 疑問（事実ではないので出典セットなし） |
| change_candidates | 変更候補（未対応 / 確認中 / 反映済み / 見送り） |
| change_log | 更新履歴（追記のみ） |
| app_settings | アプリの設定（前回の確認者名など） |
| api_fetch_log | 外部API取得の記録（Step 11 で追加） |

## 4. 画面構成

| # | 画面 | 主な内容 |
|---|---|---|
| ① | ホーム | 件数、確認待ち・再確認要の件数、横断検索 |
| ② | 製品情報 | 基本 / 適応症 / 承認・再審査 / ライセンス・特許 / 安全性 / 文書 |
| ③ | 疾患情報（MA学習） | 概要・UMN / 標準治療・ガイドライン / 関連・競合製品 / 臨床試験 / 主要論文 / エビデンスギャップ・メモ |

| ⑥ | 論文 | 一覧・所属確認待ち・属性 |

| ⑧ | 確認・更新管理 | 確認待ち、変更候補、差分、更新履歴（閲覧のみ） |
